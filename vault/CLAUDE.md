# Правила агента для базы знаний QA: <<ПРОЕКТ>>

Это база знаний QA по проекту <<ПРОЕКТ>>. Хранилище Obsidian (Markdown + YAML-фронтматтер), синхронизируется с закрытым Git-репозиторием через плагин Obsidian Git. Описание папок и статусов — в [README.md](README.md), шаблоны документов — в `Шаблоны/`.

Писать на языке пользователя (по умолчанию — по-русски). Если в рабочей папке есть общий `CLAUDE.md` с правилами, они действуют и здесь.

## Скиллы
- `kb-intake` — пользователь прислал задачу или требования: сохранить исходник, нормализовать, проверить, завести требования и вопросы.
- `kb-testcases` — написать или дополнить тест-кейсы по требованиям.
- `kb-change` — функционал поменялся, пришёл ответ на вопрос, прошёл прогон: внести правки и отметить, что затронуто.

## Платформа
Поле `platform` — список значений из README (например `приложение`, `веб`, `админка`, `бэкенд`). Если у продукта одна платформа, поле можно оставлять пустым или удалить из шаблонов.
- Если из источника неясно, касается ли требование всех платформ, — это вопрос, а не догадка.
- Требование к общему API заводится один раз со всеми платформами, а не копируется.
- В тест-кейсе поле `device` — устройство и версия, на которых кейс проверяется (например «Pixel 7, Android 14», «Chrome на Windows»).

## Имена файлов и ID
- Имя файла = `ID Короткое название.md`, например `REQ-0012 Поиск находит товар по артикулу.md`, `<<ПРИМЕР_ЗАДАЧИ>> Поиск по артикулу.md`.
- ID в поле `id` фронтматтера и в начале имени файла совпадают.
- Следующий номер = максимальный существующий номер в папке + 1. Номер узнавать по списку файлов папки, а не по памяти. Нумерация своя в каждой базе, 4 цифры.
- Ссылки в формате Obsidian: `[[REQ-0012 Поиск находит товар по артикулу]]`. Поле `task` — ссылка на карточку задачи в кавычках: `task: "[[<<ПРИМЕР_ЗАДАЧИ>> Поиск по артикулу]]"`.
- Файлы не переименовывать и не перемещать: Obsidian обновляет ссылки только при переименовании внутри себя. Если переименование необходимо, найти и исправить все ссылки на старое имя.

## Перед созданием документа
1. Поискать по базе (по ключу задачи, ключевым словам, экрану). Если документ уже есть, дополнить его, а не плодить дубликат.
2. Взять шаблон из `Шаблоны/` и заполнить фронтматтер: `{{date}}` заменить на сегодняшнюю дату `ГГГГ-ММ-ДД`, `{{title}}` — на заголовок.
3. HTML-комментарии `<!-- … -->` из шаблона в готовом документе удалять.

## Главные ограничения
1. **Не додумывать.** В нормализованном требовании только то, что есть в источнике. Пробел, противоречие или двусмысленность — это вопрос (`03 Вопросы`), а не догадка в тексте требования.
2. **Не принимать решения за людей.** Статус `согласовано` и поле `confirmed_by` агент ставит, только если:
   - пользователь в чате прямо сказал, что требование согласовано, или
   - есть ответ человека (комментарий в трекере, сообщение в чате), который пользователь передал.
   В `confirmed_by` — имя человека, в `source` — откуда ответ. Никогда не «AI Agent».
3. **Гипотеза ≠ факт.** Фактом называется только то, что видно напрямую: на экране, в ответе сервера, в логе, в коде. В справке (`06 Продукт`) у каждого утверждения указывать, на чём оно основано. Косвенные выводы — в раздел «Гипотезы».
4. **Атомарность.** Одно требование = одно проверяемое правило. Сложное требование разбивать на несколько REQ.
5. **Исходник дословно.** Текст задачи сохраняется в `07 Входящие` как есть, до нормализации. В требовании — дословная цитата.
6. **Изменения не затирают историю.** При правке требования добавлять строку в «История изменений» (дата, что изменилось, источник, кто подтвердил) и обновлять `updated`. Если требование заменено целиком: старое — `устарело` со ссылкой на новое. Связанные тест-кейсы — `требует обновления`.
7. **Без секретов.** Не записывать пароли, токены, ключи API, коды подтверждения. Тестовые аккаунты — только логин и где лежит пароль.
8. **Решения разработчика.** Комментарий разработчика «так задумано», «это норма» или согласованное отличие от ТЗ — это решение. Его оформлять в `04 Решения`, а не в дефекты.

## Вопросы
- Каждый вопрос — отдельный файл в `03 Вопросы`. Вопросы не удаляются, даже закрытые: по ним видна история.
- Любое событие по вопросу (заведён, задан, напомнили, ответ, база поправлена, закрыт) — новая строка в таблице «История» внизу файла: дата, что произошло, кто, где. Старые строки не править.
- Сводка всех вопросов — [[Журнал вопросов]].

## Тест-кейсы
- Проверять всю выдачу до конца, а не первые N элементов. Шаги вида «выписать первые 15» запрещены.
- В каждом кейсе есть блок «Варианты не по накатанной»: другой порядок шагов, другие данные, разные роли, пустые и граничные значения.
- Кейс связан хотя бы с одним требованием (`requirements`) или задачей.
- Результат прогона записывать, только если он реально получен. Если в источнике результат дан по разделу, а не по кейсу, — не переносить его в кейс.

## Отчёт пользователю после работы с базой
Коротко:
- что создано и изменено (ссылки на файлы);
- какие вопросы открыты и кому их задать, с готовым текстом;
- что не проверено.

## Git
Синхронизацию делает Obsidian Git. Агент сам не делает `commit`, `push`, `pull`, `reset` и не переключает ветки, если пользователь не попросил.
