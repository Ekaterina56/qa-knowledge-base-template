# Приём задачи в базу знаний

Базы перечислены в разделе «Базы знаний QA» общего `CLAUDE.md` рабочей папки: путь к базе и проект (ключ задач). Выбрать базу по проекту задачи; если проект неясен или раздела нет — спросить пользователя. Документы одного проекта в базу другого не класть.

Сначала прочитать её `CLAUDE.md` (правила, имена файлов, статусы) и нужные шаблоны из `Шаблоны/`. Писать по-русски.

## Шаг 1. Понять, что пришло
- Источник: Jira, чат, документ (docx, pdf, Confluence, Google Doc), слова пользователя.
- Проект и база. Если неясно — спросить. Ключ задачи, если есть.
- Если у продукта несколько платформ (см. README базы), Поле `platform` заполняется в карточке задачи и в каждом требовании.
- Если источник — ссылка, которую агент не может открыть, попросить пользователя прислать текст. Не восстанавливать его по памяти.

## Шаг 2. Найти, что уже есть
Grep по базе: ключ задачи, название фичи, экран. Если карточка задачи или требования уже есть, это не новая задача, а изменение: перейти к скиллу `kb-change`.

## Шаг 3. Сохранить исходник
Файл `07 Входящие/ГГГГ-ММ-ДД Ключ или тема.md`:
- фронтматтер `type: входящее`, `task`, `source` (ссылка или «чат»), `received`;
- ниже — текст дословно, без правок и сокращений.

## Шаг 4. Карточка задачи
`01 Задачи/КЛЮЧ Короткое название.md` по шаблону «Задача». Суть своими словами в 2–3 предложениях, ссылки на Jira и на исходник.

## Шаг 5. Нормализация
Разбить исходник на атомарные требования: одно проверяемое правило = один файл `02 Требования/REQ-NNNN Название.md` по шаблону.
- «Исходный текст» — дословная цитата нужного куска.
- «Нормализованное требование» — одна фраза вида «Когда <условие>, <кто/что> <делает> <результат>». Только то, что есть в источнике.
- `kind`: функциональное / нефункциональное / бизнес / интеграция / UI.
- `area` — экран или раздел приложения, как в `06 Продукт`.
- Статус `на анализе`.
- Неявные требования, которые следуют из контекста (например, «гость тоже видит»), отдельными REQ не заводить. Оформить вопросом: «подразумевается ли …?».

## Шаг 6. Верификация
Для каждого REQ заполнить таблицу «Проверка требования»:

| Критерий | Что проверить |
|---|---|
| Полнота | Есть ли условие, действие, результат? Для кого (гость, залогиненный)? На каких средах и платформах? |
| Однозначность | Можно ли понять двумя способами? Есть ли размытые слова: «быстро», «удобно», «корректно», «как обычно»? |
| Непротиворечивость | Не спорит ли с другими REQ, с `04 Решения`, со справкой в `06 Продукт`, с текущим поведением? |
| Тестируемость | Можно ли написать шаг и ожидаемый результат, который однозначно PASS или FAIL? |
| Граничные случаи и ошибки | Пустые данные, ноль, максимум, офлайн, ошибка сервера, нет прав, другая страна, язык, часовой пояс? |

- ✅ — всё ясно.
- ⚠️ — есть проблема: завести вопрос и сослаться на него.
- Если хотя бы один ⚠️, статус требования `есть вопросы`.
- Если все ✅, статус остаётся `на анализе`. `согласовано` ставит только человек (см. CLAUDE.md базы).

Противоречие с текущим поведением приложения, которое видно напрямую, — тоже вопрос, а не «баг в требованиях».

## Шаг 7. Вопросы
`03 Вопросы/Q-NNNN Коротко суть.md` по шаблону, один вопрос = одна неясность.
- «Варианты» — 2–3 трактовки. Выбор не делать.
- «Текст вопроса для отправки» — готовая формулировка от имени пользователя: коротко, вежливо, со ссылкой на место в задаче. Отправлять нельзя, это делает пользователь.
- `to`: разработчик / продакт / лид, если понятно, кому вопрос.
- В таблицу «История» — первая строка: дата, «Вопрос заведён», кто, откуда. Если вопрос уже задан в Jira или чате — вторая строка с этим событием и статус `задан`.

Перед созданием вопроса проверить `04 Решения` и закрытые вопросы: возможно, ответ уже есть.

## Шаг 8. Связи
- Карточку задачи дополнить ссылками на все REQ и Q.
- В каждом REQ заполнить «Связи».

## Шаг 9. Отчёт пользователю
- сколько требований заведено, ссылки;
- открытые вопросы списком с готовым текстом для отправки, сгруппированные по адресату;
- что не удалось разобрать и почему;
- предложить следующий шаг: написать тест-кейсы (`kb-testcases`) — для согласованных требований или черновиком для тех, что на анализе.
