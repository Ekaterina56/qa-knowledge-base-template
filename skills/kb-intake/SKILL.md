# Приймання задачі в базу знань

Бази перелічено в розділі «Бази знань QA» загального `CLAUDE.md` робочої папки: шлях до бази й проєкт (ключ задач). Вибрати базу за проєктом задачі; якщо проєкт незрозумілий або розділу немає — запитати користувача. Документи одного проєкту в базу іншого не класти.

Спершу прочитати її `CLAUDE.md` (правила, імена файлів, статуси) і потрібні шаблони з `Шаблони/`. Писати мовою користувача.

## Крок 1. Зрозуміти, що надійшло
- Джерело: Jira, чат, документ (docx, pdf, Confluence, Google Doc), слова користувача.
- Проєкт і база. Якщо незрозуміло — запитати. Ключ задачі, якщо є.
- Якщо в продукту кілька платформ (див. README бази), поле `platform` заповнюється в картці задачі й у кожній вимозі.
- Якщо джерело — посилання, яке агент не може відкрити, попросити користувача надіслати текст. Не відновлювати його з пам'яті.
- Вивантаження Jira (Export → Word, файл .doc) перетворити на текст скриптом `scripts/jira-doc-to-text.js` із шаблону бази, якщо він доступний.

## Крок 2. Знайти, що вже є
Пошук по базі: ключ задачі, назва фічі, екран. Якщо картка задачі або вимоги вже є, це не нова задача, а зміна: перейти до скілу `kb-change`.

## Крок 3. Зберегти джерело
Файл `07 Вхідні/РРРР-ММ-ДД Ключ або тема.md`:
- frontmatter `type: вхідне`, `task`, `source` (посилання або «чат»), `received`;
- нижче — текст дослівно, без правок і скорочень.

## Крок 4. Картка задачі
`01 Задачі/КЛЮЧ Коротка назва.md` за шаблоном «Задача». Суть своїми словами у 2–3 реченнях, посилання на трекер і на джерело.

## Крок 5. Нормалізація
Розбити джерело на атомарні вимоги: одне правило, яке можна перевірити, = один файл `02 Вимоги/REQ-NNNN Назва.md` за шаблоном.
- «Вихідний текст» — дослівна цитата потрібного фрагмента.
- «Нормалізована вимога» — одна фраза на кшталт «Коли <умова>, <хто/що> <робить> <результат>». Лише те, що є в джерелі.
- `kind`: функціональна / нефункціональна / бізнес / інтеграція / UI.
- `area` — екран або розділ продукту, як у `06 Продукт`.
- Статус `на аналізі`.
- Неявні вимоги, що випливають із контексту (наприклад, «гість теж бачить»), окремими REQ не заводити. Оформити питанням: «чи мається на увазі …?».

## Крок 6. Верифікація
Для кожної REQ заповнити таблицю «Перевірка вимоги»:

| Критерій | Що перевірити |
|---|---|
| Повнота | Чи є умова, дія, результат? Для кого (гість, залогінений)? На яких середовищах і платформах? |
| Однозначність | Чи можна зрозуміти двома способами? Чи є розмиті слова: «швидко», «зручно», «коректно», «як зазвичай»? |
| Несуперечливість | Чи не суперечить іншим REQ, `04 Рішення`, довідці в `06 Продукт`, поточній поведінці? |
| Тестованість | Чи можна написати крок і очікуваний результат, який однозначно PASS або FAIL? |
| Граничні випадки й помилки | Порожні дані, нуль, максимум, офлайн, помилка сервера, немає прав, інша країна, мова, часовий пояс? |

- ✅ — усе зрозуміло.
- ⚠️ — є проблема: завести питання й послатися на нього.
- Якщо хоча б один ⚠️, статус вимоги `є питання`.
- Якщо всі ✅, статус лишається `на аналізі`. `погоджено` ставить лише людина (див. CLAUDE.md бази).

Суперечність із поточною поведінкою продукту, яку видно напряму, — теж питання, а не «баг у вимогах».

## Крок 7. Питання
`03 Питання/Q-NNNN Коротко суть.md` за шаблоном, одне питання = одна неясність.
- «Варіанти» — 2–3 тлумачення. Вибору не робити.
- «Текст питання для надсилання» — готове формулювання від імені користувача: коротко, ввічливо, з посиланням на місце в задачі. Надсилати не можна, це робить користувач.
- `to`: розробник / продакт / лід, якщо зрозуміло, кому питання.
- У таблицю «Історія» — перший рядок: дата, «Питання заведено», хто, звідки. Якщо питання вже поставлене в трекері чи чаті — другий рядок із цією подією і статус `поставлене`.

Перед створенням питання перевірити `04 Рішення` і закриті питання: можливо, відповідь уже є.

## Крок 8. Зв'язки
- Картку задачі доповнити посиланнями на всі REQ і Q.
- У кожній REQ заповнити «Зв'язки».

## Крок 9. Звіт користувачу
- скільки вимог заведено, посилання;
- відкриті питання списком із готовим текстом для надсилання, згруповані за адресатом;
- що не вдалося розібрати й чому;
- запропонувати наступний крок: написати тест-кейси (`kb-testcases`) — для погоджених вимог або чернеткою для тих, що на аналізі.
